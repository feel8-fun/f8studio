# Studio Agents

Open a project in the Graph editor and click the Agent button in the graph toolbar. Studio opens an Agent window bound to that project; you can keep it beside the graph while the model works. Select a configured model provider and create a session. The model can search the installed node catalog, inspect exact operator specifications and current graph ports, construct graph nodes, analyze and update a Python Script node's `code` field, deploy a project, and inspect runtime monitors and recent logs. Graph patches, code writes, deployments, and Unity installation require approval in the session. The approval card summarizes graph patch operations and can expand to show every operation and the exact patch. Other previews remain available in session artifacts.

The first request gives a new session a short title automatically. Use the pencil button beside the title to rename it. The trash button deletes a finished session and its conversation history without changing the project graph. Stop a running session before renaming or deleting it. Completed tool calls are grouped in the conversation; expand a group or an individual call to inspect arguments and results.

Use **Settings** in the top bar or **Configure providers** in the Agent window to manage model connections. Only saved connections and configured environment connections are listed. **New connection** creates a named account or host using OpenAI Responses, OpenAI-compatible Chat Completions, Anthropic Messages, or System-One decisions; several connections can use the same protocol with separate URLs and keys. Use **Detect models** to query the connection's model-list endpoint, or **Refresh models** on an existing connection, then save the updated list. When a host does not list models, enter an ID manually. **Test model** makes one small inference request, including a typed Choice question for System-One, which may be billable. Model listing verifies the catalog endpoint and credentials but does not prove inference or tool use. Finish or cancel active runs before changing saved connections.

Connection settings are saved in `agent-providers.json` in the Studio data directory, with private file permissions on POSIX. Saved settings override environment defaults. Each named connection has its own credential and model list; keys remain on the server and are never returned by the settings API. Leave the key blank to retain it, or select **Remove saved API key** to clear it. Use the conversation header to change the connection or model for the next turn of an existing session; an active run keeps its starting model and must finish or be stopped before switching. Any listed connection, including an older OpenAI entry, can be deleted. A deleted environment-backed entry stays hidden without changing the environment variable. Deleting a connection leaves old session history intact, but those sessions need another connection before they can run again.

Image input is enabled per selected model when its model catalog explicitly reports image support or you confirm support for that model in provider settings. Some providers omit capability metadata; Studio shows **Unknown** instead of guessing from a model name or protocol. The image and reasoning controls show API metadata or a manual per-model confirmation; their tooltips identify the source. Refreshing models preserves manual confirmations for models still listed by the provider. Clear a confirmation and refresh to use the provider's current value again. Reasoning support means the model accepts a reasoning-effort parameter; it does not expose the model's internal reasoning. In an agent session, the reasoning-effort selector applies to the next run: Auto sends no effort parameter, while Low, Medium, or High is sent using that connection's API protocol. A model or gateway may reject an effort level it does not support. Existing custom connections that previously had the image checkbox enabled retain that setting only for their original default model, labeled **previous setting** until the host reports capability metadata. Supported models accept up to three PNG, JPEG, WebP, or GIF images per message (4 MB each); images remain visible in session history and can be used in follow-up turns. Audio and video are not supported in the agent composer.

The deterministic provider remains available as a fixed graph-building example. Select a configured model provider for open-ended graph, code, and game tasks.

System-One connections are for [Decision nodes in graphs](decision-models.md), not chat sessions. They evaluate Choice, Score, and Noul questions and return typed probabilities. This protocol uses Studio's HTTP client and does not require an Agent Framework package upgrade.

The agent can list and read workflow skills. Studio includes `graph_python` and `unity_modding`. Add a game-specific skill at `<Studio data directory>/agent-skills/<skill-id>/SKILL.md`; the skill ID may contain lowercase letters, digits, underscores, and hyphens. A local skill with the same ID overrides a bundled skill. Skills provide workflow context; game-directory changes still go through Studio's typed preview and approval tools.

Unity targets can be detected, previewed, installed through the managed setup tool, and checked for decoded UDP skeleton frames. Unreal detection is available, but Studio does not yet provide a verified UE4SS installer. The agent cannot install an Unreal patch through Studio until that tool exists.

Code changes are committed to the project graph, not to source files in the repository. A code write requires the graph revision and source hash returned by the last code read; a conflicting edit must be read and reconciled again. Unsaved text in another browser editor window is not visible to the agent, so save or discard that draft before approving a code change.
