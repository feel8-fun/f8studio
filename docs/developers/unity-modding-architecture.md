# Unity Modding Architecture

Unity support is split across a pinned exporter toolchain, shared typed protocol
code, PyEngine motion operators, and the Web Studio guided workflow. The split is
intentional: game-specific discovery and C# builds stay in the submodule, while
packet interpretation and graph behavior remain part of the F8Studio public
runtime.

## Repository Ownership

| Area | Owner | Responsibility |
| --- | --- | --- |
| `external/f8unitymods` | Git submodule | Unity profiles, backend detection, managed installation, C# exporters, release assets |
| `packages/f8pysdk/f8pysdk/motion` | F8 Python SDK | Typed skeleton models and binary/JSON decoding |
| `packages/f8pyengine/f8pyengine/operators` | PyEngine | Stable selection, relative pose axes, watchdog, TCode processing |
| `packages/f8studio_server/f8studio_server/local_integration.py` | Web Studio server | Detect/preview/apply/verify orchestration and local safety boundary |
| `scripts/unitymods_ci.py` | Root build | Submodule validation, build/package dispatch, SHA-256 bundle manifest |

`external/f8unitymods` is the only authoritative Unity checkout. Runtime code
imports the packaged `f8unitymods_setup` API directly; it does not search for a
sibling repository or mutate `sys.path`.

Initialize and validate it with:

```bash
git submodule update --init --recursive
pixi run -e default unitymods_validate
```

## Installation Boundary

The public workflow is a transaction with an explicit approval point:

```text
detect -> diagnose -> preview exact writes -> confirm -> apply
```

Detection and preview are read-only. Apply is allowed only after confirmation.
Neither CI nor root packaging accepts a game directory, so build automation
cannot accidentally install into a local game. Managed profiles and custom
configuration preservation rules remain owned by `f8unitymods_setup`.

### BepInEx completeness

Detection reports BepInEx as installed only when all of these components exist:

```text
BepInEx/core/BepInEx.dll (v5 Mono), or
BepInEx/core/BepInEx.Unity.Mono.dll (v6 Mono), or
BepInEx/core/BepInEx.Unity.IL2CPP.dll (v6 IL2CPP)
doorstop_config.ini
winhttp.dll
```

A lone bootstrap file, an exporter-only `BepInEx/plugins` directory, an
auxiliary `BepInEx*.dll` without a loader entry point, or loader core files
without both bootstrap files are reported as a partial installation.
The install preview then proposes `repair_incomplete_bepinex` and lists the
loader paths it may restore. If existing core files identify a Mono/IL2CPP
variant that conflicts with the detected game backend, installation is blocked
until the user explicitly previews and confirms a forced replacement. Apply
performs the repair from the backend-specific official BepInEx archive and then
reruns completeness detection; missing components make the install fail with an
actionable error instead of allowing exporter installation to appear successful.

## LMEX V2 Contract

The exporter sends little-endian UDP datagrams. Strings are UTF-8, NUL
terminated, and padded with zero bytes to a four-byte boundary.

```text
modelName, timestampMs:u64, schema, boneCount:i32
bone[] = name, position:3xf32, rotation(wxyz):4xf32
"LMEX", version:u16, frameId:u64,
chunkIndex:i32, chunkCount:i32, totalBoneCount:i32, characterId:i32
v2 identity = profileId, role, roleIndex:i32, exporterVersion
optional "ANIM" = normalizedTime:f32, layerIndex:i32, clipName, poseKey
```

LMEX v1 remains decodable. V2 adds stable character identity:

```text
profileId:role:roleIndex
```

For example, `hs2:female:0` remains stable when a runtime model name changes.
Legacy packets fall back to an explicitly selected exact `modelName`; they are
never guessed into a stable role.

The checked-in fixture is generated by compiling the production
`SkeletonPacketEncoder.cs`, not a second handwritten encoder. Run:

```bash
pixi run -e default unitymods_contract
```

On Windows this regenerates the fixture through C# and requires byte-for-byte
equality before decoding it with `f8pysdk.motion`. The decoder rejects bad
alignment, truncation, unsupported extensions, invalid chunk metadata, and
unknown trailing data with `SkeletonPacketDecodeError`.

## UDP Skeleton Data Semantics

Verification distinguishes transport activity from usable motion data:

- `packetCount` counts received UDP datagrams.
- `decodedFrameCount` and `sampleCount` count complete decoded frames.
- Multi-chunk frames count only after every chunk is assembled.
- Invalid traffic produces `listenerStatus=packets_rejected`.
- Success requires `listenerStatus=verified` and a positive decoded frame count.

These counters and decoder timings are high-frequency evidence and stay on
report/data/monitor channels. They are not service `stateFields`.

## OSR Graph Contract

The generated graph uses explicit typed stages:

```text
UDP In -> Skeleton Decoder -> Skeleton Selector -> Bone Selector
reference + target -> Relative Pose Axes.L0
-> Envelope -> Range Map -> Smooth Filter -> Rate Limiter
-> TCode.L0 -> TCode Viz -> Serial Out
```

Selectors match `profileId`, `role`, and `roleIndex`. `Relative Pose Axes`
computes translation and rotation in the reference bone's local frame; the MVP
L0 path defaults to local Y. Calibration, travel range, smoothing, and rate
limits are ordinary graph nodes so authors can inspect and replace each stage.

Physical output has two independent safeguards:

```text
Tick 50 Hz -> Stream Watchdog.check
Skeleton Decoder.skeletons -> Stream Watchdog.value
Stream Watchdog.valid -> Serial Out.exec
```

The watchdog expires after 250 ms, and `Serial Out.enabled` defaults to `false`
globally and in the generated graph. Do not remove either guard from reusable
recipes.

## Build And Distribution

Root tasks delegate into the pinned submodule:

```bash
pixi run -e default unitymods_build
pixi run -e default unitymods_test
pixi run -e default unitymods_package
```

Windows distribution builds place setup wheels, exporter archives, release
manifests, and `f8unitymods-bundle.json` under `unitymods/`. The bundle manifest
records the submodule commit, dirty flag, size, source path, and SHA-256 for each
asset. Duplicate release filenames are rejected instead of overwritten.

Local Python packages are built as non-editable wheels. Pixi locks third-party
dependencies from the root lock seed; `install_env.bat` then installs only the
local wheels owned by each runtime feature with `pip --no-deps --no-index`.
This avoids source-tree dependencies and keeps ONNX/MediaPipe packages out of
the Studio environment unless their feature owns them.

## Nested Commit Order

Submodule changes require two commits:

1. Commit exporter/setup changes inside `external/f8unitymods` and publish that
   commit to the submodule remote.
2. In the root repository, stage the updated submodule gitlink together with
   F8Studio changes and commit them.

A root commit made before the inner commit only records the old gitlink and
cannot reproduce the new exporter implementation.
